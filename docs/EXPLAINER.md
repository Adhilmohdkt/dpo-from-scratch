# DPO implementation notes

## Objective

For a prompt `x`, preferred response `y+`, rejected response `y-`, trainable policy `πθ`, frozen reference `πref`, and temperature `β`, the standard sigmoid DPO loss for one pair is:

`-log σ( β [ (log πθ(y+|x) - log πθ(y-|x)) - (log πref(y+|x) - log πref(y-|x)) ] )`.

The code sums token log-probabilities over each response. It computes the DPO arithmetic in float32 even when model weights/activations use fp16. `logsigmoid` is used for stability; non-finite loss and gradient norms stop training.

## Prompt and response boundaries

The tokenizer's `apply_chat_template` formats the prompt with a generation prefix and formats the complete conversation separately. Token IDs are checked to ensure the prompt rendering is an exact prefix of the full conversation. Loss masks cover assistant response targets and EOS, excluding the prompt. Right padding is represented by a separate attention mask and is excluded from response masks. Overlong prompts are left-truncated to preserve the response; overlong responses are truncated and explicitly terminated by EOS.

Instruction models use their own published chat template. A simple fallback exists only for base/tiny models without a template.

## Why the SFT adapter is the reference

At the beginning of DPO, the reference policy must be exactly the policy produced by SFT. Disabling a LoRA adapter would instead evaluate the underlying base model. This implementation saves the SFT adapter, reloads it as a frozen reference, computes chosen/rejected reference log-probabilities over the fixed training examples, writes those values and identity metadata to disk, and releases the reference model. The DPO policy is separately reloaded from the same SFT adapter and then updated. The cache is reusable only when checkpoint digest, model, data split, row count, and max sequence length match.

This trades one precomputation pass and local disk for lower accelerator memory use. SFT writes a manifest with the resolved Hub commit (or content hashes for local base-model files) and tokenizer/template identity. DPO refuses adapters without this manifest, pins model loads to the recorded base revision, and validates tokenizer identity before scoring. The reference-cache key also includes the SFT adapter digest, resolved base identity, dataset fingerprint/revision, train split and subset settings, deterministic seed, preprocessing version, tokenizer identity, and maximum sequence length. Corrupt, non-finite, wrong-shape, or metadata-mismatched caches are recomputed. Changing any data selection later requires a correspondingly selected reference cache or a cache regeneration.

## Dataset assumptions and selection experiment

UltraFeedback Binarized provides `chosen` and `rejected` as two-message lists and SFT `messages`; the preference split includes `prompt_id` and scalar `score_chosen` / `score_rejected` values. The [dataset card](https://huggingface.co/datasets/HuggingFaceH4/ultrafeedback_binarized) describes GPT-4 scoring the candidate completions and chosen as the highest overall score. The loader assigns stable source row IDs before split/capping so experiment manifests can target an exact candidate subset.

The simplified research add-on defines an **external reward-score margin** as `score_chosen - score_rejected` using those dataset scalar fields, before any DPO updates. It selects the largest margins, with row ID as a deterministic tie-break. Its comparator samples uniformly without replacement from the same post-validation, post-cap train candidates, using the configured seed, and has exactly the same subset size. The full-data arm is all rows in that same candidate pool (the train split minus validation and, if configured, the sample cap). Validation IDs are explicitly rejected by the data loader; final test rows are never loaded by the selector. The command `python -m scripts.select_preference_data --config ... --subset-size N --output-dir ...` writes selected/random IDs, full candidate IDs, candidate score/margin CSV, seed, dataset revision/fingerprint, selection metadata, and the training config snapshot.

Train each arm from the same SFT output with its own DPO output/cache path (`--output-dir` and `--reference-logps-path`); this keeps checkpoints and reference caches from overwriting one another. The Colab notebook optionally runs all three arms and evaluates them together on validation. For independent seeds, create a new seed-specific config/output directory and rerun selection with that seed.

This is a simplified experiment inspired by [Deng et al., *Less is More*](https://arxiv.org/abs/2502.14560), not a reproduction. The referenced paper proposes margin maximization with a Bayesian aggregation of external and implicit margin sources; this implementation uses a single dataset-provided scalar-score difference and does not use implicit DPO margins, pilot training, or the paper's aggregation procedure. No improvement is assumed.

## Checkpoint resumption

Periodic checkpoints contain the PEFT adapter plus optimizer/scheduler state, random number generator states, global step, epoch, run-configuration digest, sequential batch cursor, and (for SFT checkpoints) the model/tokenizer manifest. Sequential batches use a fixed deterministic data order to make the next batch resumable. A resume request with different run metadata is rejected. Training has finite-loss and finite-gradient-norm guards. Checkpoint recovery has unit-test coverage but interruption/restart has not been tested during a full dataset run.

## Comparison and research caveats

The trainers may use their own deterministic training-split partition for progress monitoring. Evaluation uses a separate deterministic partition of the official `test_prefs` data: 500 validation pairs and a disjoint 500-pair final test set, with the remaining 1,000 rows unused. Validation and final-test rows are excluded from training and preference-data selection. The evaluator loads only the requested partition; use `--split test` after model and beta choices are fixed. It reports chosen-vs-rejected response sequence-log-probability accuracy and margins. An exact tie receives half credit, so a policy identical to its reference reports 50% accuracy. Accuracy includes a 95% Wilson score interval; ties contribute fractional successes to that interval. For DPO checkpoints, the evaluator can also report implicit rewards relative to the exact SFT reference. It exports deterministic generated responses, their token lengths, and whether each generation reached the 256-token cap. Generated text is not automatically quality-scored; these diagnostics are not a human preference benchmark, and longer responses are not assumed to be better.

Base, SFT, and DPO are generated in the same evaluation invocation with the same `max_new_tokens: 256` and deterministic decoding. Evaluation writes per-example response-length CSVs plus aggregate metrics CSV/JSON, including mean length and cap-hit fraction. Response length is descriptive and is not interpreted as better alignment. `scripts/aggregate_results.py` pools actual `metrics.csv` files by split/checkpoint/beta and seed, reporting a mean and sample standard deviation only from available runs; one-seed standard deviation is blank. No output is fabricated when runs are absent.

### Scaled experiment plan and restart behavior

Use `notebooks/colab_scaled_run.ipynb` for the time-boxed comparison. It writes checkpoints and logs to a private Hugging Face Hub repository; it does not depend on Drive. Store a write-enabled access token in Colab Secrets as `HF_TOKEN`, and enter the private repository ID in the notebook. The code reads the token from the environment and does not print or save it.

A fresh Tesla T4 measured 50 optimizer steps on 400 actual UltraFeedback training examples with length 512, batch size 1, and gradient accumulation 8. SFT averaged 3.058 seconds per optimizer step and DPO averaged 6.119 seconds. Their complete process times, including setup and final saves, were 176.4 and 406.9 seconds. Sampled memory readings were 2,403 MiB during SFT and 2,739 MiB during DPO; these were not peak measurements. The run's per-step logs are retained at `results/scaled-t4-512/timing-smoke/raw`.

The runnable configs pin UltraFeedback to commit `3949bf5f8c17c394422ccfab0c31ea9c20bdeb85`. Each stage stores the loaded split's dataset fingerprint and row-ID hash in `dataset_identity.json`; checkpoints include the same identity in their resume metadata. Resume fails if the source fingerprint or selected rows differ. Validation loading selects only its reserved row-index range. The final-test range is not selected or read unless the evaluator is explicitly called with `--split test`.

`configs/scaled_t4.yaml` caps each full-data arm at 512 pairs, uses equal 128-row margin-selected and random subsets, and uses one seed (42). The estimated optimizer work for one SFT and four DPO runs is about 1,174 seconds (19.6 minutes). This estimate excludes model and data loading, reference scoring, checkpoint uploads, and generation. The completed evaluation used six checkpoints on a 200-example validation subsample and up to 256 generated tokens; its runtime was not captured in the local record. The original experiment reserved a 500-example validation set, but this reduced run is not equivalent evidence. The one-seed plan reflected the three-hour budget and did not promise completion within that limit.

Training writes JSONL and CSV metrics every optimizer step. Checkpoints are saved every 10 steps and uploaded with those metrics. After a disconnection, rerun the same notebook cell with the same Hub repository and config. The runner restores each stage snapshot, skips stages marked complete under the same configuration, and resumes an interrupted stage from its latest optimizer checkpoint. If data, subset IDs, or training settings change, use a new output directory/run prefix. The five configured seed-42 scaled stages are reported complete: SFT and each of the beta 0.1 and 0.5 full arms completed 64 optimizer steps; margin-selected and random arms completed 16 steps each.

A six-checkpoint evaluation on a deterministic 200-example subset of the original 500-example validation slice was reported from Colab, with greedy generation capped at 256 tokens. Its CSV/JSON metric outputs are not available in the local checkout or committed history, and could not be restored from the private Hub in this environment. The evaluation-only workflow and expected private Hub path are described in [EVALUATION_ONLY.md](EVALUATION_ONLY.md) and [the results inventory](../results/README.md).

The committed 32-example pilot CSV is available and supports the pilot table in the README. Its generation cap was 64 tokens, so those pilot values must not be conflated with the later 200-example run. The pilot showed no raw accuracy change among the seven checkpoints on that sample. The later 200-example findings cannot be independently confirmed from the artifacts currently published.

The evaluator's reported preference accuracy compares raw policy response sequence log-probabilities for chosen and rejected answers. The implicit reward margin compares the policy's chosen/rejected log-probability difference against the SFT reference and scales it by beta. These metrics answer different questions. The evaluator does not calculate implicit-reward pairwise accuracy. The proposed 500-example audit of that metric was not implemented or run; it is future work, not a project result.

The DPO loss was audited against the original paper and no confirmed loss bug was found. Reference loading/freezing, cache identity, prompt/padding masking, and EOS handling were reviewed. The small model, capped training subsets, one seed, 200 validation pairs, and synthetic preference supervision limit what can be concluded. The untouched final-test set has not been evaluated.

## Real-data pilot record

An actual one-seed T4 pilot used `configs/pilot_128.yaml`: Qwen2.5-0.5B-Instruct, UltraFeedback `train_sft` and `train_prefs`, seed 42, maximum sequence length 512, and a 128-example training cap. The split produced 32 held-out validation examples. SFT ran one epoch (16 optimizer steps). Three DPO beta runs (0.05, 0.1, 0.5) each started from that exact SFT adapter and used the same 128 preference pairs. At beta 0.1, the margin-selected and random arms each used 32 rows from those 128 training candidates; their selected IDs, candidate margins, and config snapshots are saved under `results/pilot-128/selection` and `results/pilot-128/configs`. The 128-row beta-0.1 run is the full-candidate-pool comparator for this pilot. The selector used only dataset-provided external scalar margins `score_chosen - score_rejected` before DPO updates. Validation and final test rows were not used for selection.

The same 32 validation examples were evaluated for Base, SFT, all three beta runs, and both selected-subset runs with greedy decoding, batch size 1, and `max_new_tokens=64`. Preference accuracy was 0.5625 for every checkpoint. Mean implicit reward margins for beta 0.05, 0.1, 0.5, margin-selected, and random were 0.0931, 0.1606, 0.4474, 0.0970, and 0.0743. Mean generated lengths were 53.88 Base, 50.69 SFT, 54.66 / 54.63 / 51.56 for the beta sweep, 51.00 for margin-selected, and 48.59 for random. All median lengths were 64 due to the generation cap. The aggregate chosen-minus-rejected log-probability means were negative while their medians were positive, showing a strongly skewed distribution that needs per-example analysis. The metrics and predictions are in `results/pilot-128/evaluation/validation`; a comparison plot is at `results/pilot-128/plots/validation_comparison.png`. Longer generations are not treated as better, and these 32-example results do not establish a meaningful preference-quality difference.

SFT took 78.4 seconds and peaked at 2,014 MiB allocated GPU memory. Each 128-pair beta DPO run took 141.2–141.9 seconds and peaked at 2,333 MiB. The 32-pair margin and random runs took 51.2 and 50.9 seconds. The seven-checkpoint validation process took 851 seconds by Colab MCP process wall time; peak memory for that combined evaluation was not measured. Mean logged per-step losses were 250.758 for SFT, 0.622 / 0.576 / 0.471 for beta 0.05 / 0.1 / 0.5, and 0.618 / 0.626 for margin-selected / random. SFT loss is response-token-summed cross-entropy and is on a different scale from the DPO pairwise logistic loss; the summary CSV also records final-step losses. Exact configs, train logs, evaluation metrics, selection IDs, and resource records are retained under `results/pilot-128`. Adapter weights were copied into the local ignored checkpoint directories and are not tracked in Git.

This is a pilot only. The full 61,135-row SFT and preference splits, repeated seeds, the full-scale margin/random/full experiment, and final-test evaluation remain incomplete. Drive authorization timed out, so no artifact was written to Drive or tested for Drive recovery. The pilot files were pulled from Colab's ephemeral filesystem into the local repository before releasing the runtime. This selection experiment is still a simplified inspired study, not a full reproduction of *Less is More*.
